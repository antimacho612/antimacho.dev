# 記事を書く

記事は `src/content/posts/<カテゴリ>/<スラッグ>.mdx` に置くだけで、ホーム・サイドバー・
カテゴリページに載る。index への登録や配線は不要。
書き方の詳細は [src/content/README.md](../../../src/content/README.md) にまとまっている。

進め方は **調査 → 判定 → 設計 → 執筆 → 検証 → 報告** の 6 ステップ。
**調査を飛ばして書き始めない** — 同じ話題が別のタイトルで既にあることはよくある。

## 1. お題を理解する

入力の形に応じて情報を集める。

- **URL** — WebFetch で取得する。一次情報（MDN・仕様書）なら、そこから何を抜き出して
  記事にするかを決める。ブログ記事なら要点だけ拾い、丸写しにはしない
- **コードスニペット** — 貼られたコードをそのまま読む。何を確かめたいのかが曖昧なら聞く
- **お題のみ**（「box-sizing の違い」等） — そのまま扱ってよい

**このサイトの主眼は「動かして確かめられること」** なので、この段階で
「読者（＝将来の自分）は何を動かせれば納得するか」を 1 つ決めておく。それがデモになる。

## 2. 重複を調べる

`src/content/posts/**/*.mdx` を Glob で列挙し、各ファイルの frontmatter
（`title` / `summary` / `tags`）を読む。本文全体まで読む必要はない。

**タイトルが違っても実質同じ話なら重複とみなす**（キーワード一致だけに頼らない）。

| 判定 | 対応 |
| --- | --- |
| 同じ内容が既にある | 作らず、該当記事を示して終了する |
| 近いが差分がある | **差分を説明したうえでユーザーに確認する** — 新規作成か既存への加筆かは委ねる |
| 該当なし | そのまま進む |

## 3. カテゴリとスラッグを決める

既存のディレクトリ（`src/content/posts/` を見る）から選ぶ。
新しいカテゴリを作るのは、既存のどれにも入らないときだけ。作る場合は
[src/site.config.ts](../../../src/site.config.ts) の `CATEGORIES` にも追加するか確認する。

スラッグは kebab-case の英語。URL に出るので短く（`grid-auto-fit-and-auto-fill` 程度）。

タグは既存の語彙を再利用する（全記事の `tags` を横断で見る）。増やしすぎると絞り込みが効かない。

## 4. デモを設計する

**先にデモを決めてから本文を書く。** 何をどう動かせば違いが見えるかが記事の骨になる。

| 使うもの | 目安 |
| --- | --- |
| `<Sandbox>` | 20 行程度までのデモ。記事にそのまま書く |
| `<Demo id="...">` | それより大きいもの、特に JS を伴うもの。`src/demos/<id>/` に置く |
| `<Compare>` | 「これを付けるとこう変わる」を 2 つ並べて見せるとき |

`<Demo>` を作る場合は [add-demo](../add-demo/SKILL.md) の手順に従う。
デモが横長になるなら `bleed` を付ける。

## 5. 書く

[src/content/_templates/post.mdx](../../../src/content/_templates/post.mdx) をコピーして書き換える。
迷ったら既存記事を 1〜2 本読んで粒度と文体を揃える。

- 常体（だ・である）。「〜します」「〜しましょう」は使わない
- **説明より先にデモを置く**
- `##` は 3〜6 個程度。`#` は書かない（タイトルから自動で入る）
- `createdAt` は今日の日付。`draft` は完成しているなら消すか `false`
- 一次情報があれば末尾に `<LinkCard>` で貼る

使えるコンポーネントは import 不要でそのまま書ける。一覧と props は
`src/content/posts/General/mdx-components.mdx` に実物付きでまとまっている。

## 6. 検証する

```bash
npm run check   # 型と frontmatter（スキーマ違反はここで落ちる）
npm run build   # ビルドが通るか
```

デモを入れたなら **`npm run dev` で実際に開いて目視確認する**。
特に見るのは次の 3 点。

1. デモが意図どおり動くか（iframe の中は隔離されているので、外から DOM は確認できない）
2. iframe に不要なスクロールバーが出ていないか（横に溢れていることが多い）
3. ダークモードに切り替えても破綻しないか

## 7. 報告する

- 調査結果（重複はなかった／近いものがあって確認した）
- 作成したファイルパスと URL
- 埋め込んだデモの種類と、それで何が確かめられるか
- check / build の結果と、目視確認したこと
